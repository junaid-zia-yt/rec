# AI Evaluation Report — Build Phase 14, Wave 2a

**Scope:** deterministic guardrails, prompt design, and eval-harness coverage across every AI workflow in `apps/web/lib/ai/`, `lib/outreach/`, `lib/matching/`, and `lib/copilot/`. This report also documents a new, versioned synthetic eval dataset (`apps/web/lib/ai/eval-fixtures/`) and the deterministic tests built against it.

## What could, and could not, be evaluated (read this first)

`anthropicConfigured` is `false` everywhere in this environment (`apps/web/lib/env.ts`) — **no live Anthropic API call has ever run in this project's history**, in this wave or any prior one. Every workflow ships as a typed provider interface plus a deterministic offline test double, and every existing test (Phase 4/6/7/9/11) and every test added this wave exercises the test double, never a live model.

**What this review could evaluate directly, with confidence:**

- The deterministic rule logic that computes mandatory gates and final scores (`lib/matching/gates.ts`, `scoring.ts`, `evaluate.ts`) — pure TypeScript, executed for real, no mocking needed.
- The evidence/unsupported-claims validators (`lib/outreach/unsupported-claims.ts`, `lib/copilot/evidence-guardrail.ts`) — pure functions, executed for real.
- The prompts' own text — whether they state the injection-defense framing, the evidence-citation requirement, and the never-invent instruction correctly.
- Whether the deterministic layer's input types (`FrozenRequirement`, `MatchRequirementAssessment`) have any structural channel for a name/university/demographic signal to influence a score — they do not, and this was proven by an executable paired-candidate test, not just a type-signature reading.
- Whether the existing and new eval harnesses' deterministic test-double providers behave the way their prompts instruct a real model to behave, as a **proxy** for real-model behavior.

**What this review could NOT evaluate, and could not fix:**

- Real model behavior against any of these prompts — whether Claude actually follows the injection-defense framing, actually refuses to invent evidence, actually classifies an adversarial reply as `ambiguous` rather than obeying it. Nothing in this codebase has ever observed that.
- Real bias testing (docs/10-ai-evaluation-guardrails.md §10.7) — this requires paired-CV probes run through a live model and ideally real historical outcome/adjudication data, neither of which exists here. This review's bias-probe fixture (§14 below) only proves the **deterministic** scoring/gate layer has no structural channel for a demographic-adjacent signal to enter a score; it says nothing about a live model's own semantic judgment.
- Ranking-quality (Kendall's tau vs. human rankings), extraction precision/recall against real adjudicated JD/CV pairs, or any of docs/10-ai-evaluation-guardrails.md §10.1/§10.5/§10.9's ground-truth-dependent metrics — no ground-truth dataset exists yet (§10.1 is explicitly marked `[CLIENT CONFIRM]`, unresolved).

Any claim below that a workflow "is safe" or "behaves correctly" is a claim about its **deterministic guardrails and prompt design**, never about live model output.

## Findings

### Finding A (Medium) — `ai_prompt_versions` is a documented mechanism that does not actually exist in the running system

**Claim in docs/09-ai-architecture.md §9.5:** "`AI_prompt_versions` stores every template with a semantic version; `AI_runs` references the exact version used... Changing a prompt is a deployable change subject to the same eval suite before promotion."

**What is actually true today:**

- `public.ai_prompt_versions` (`supabase/migrations/0017_ai_runs.sql`) exists as a table, but **no application code anywhere inserts a row into it** — confirmed by grep across `apps/web/lib` and `apps/web/scripts`/`supabase/seed`. It is a dead table.
- `ai_runs.prompt_version` is `text not null` with **no foreign key or CHECK constraint** tying it to `ai_prompt_versions.version` — nothing in the database enforces that a value written there corresponds to a real, versioned template.
- The actual mechanism that exists is: a TypeScript `const ..._PROMPT_VERSION = '...-v1'` string co-located with each prompt's text, plus a comment instructing a developer to "bump this any time the wording changes." This is **pure convention**, not a structural guarantee — nothing stops a developer editing `REQUIREMENT_EXTRACTION_SYSTEM_PROMPT`'s wording without bumping `REQUIREMENT_EXTRACTION_PROMPT_VERSION`, and no test in the repository checks that the two stay in sync (a hash-of-template-text-must-match-version-string test would close this, but does not exist today).

**Impact:** the audit trail (`ai_runs.prompt_version`) is real and does get written on every call, so Core Principle #10 ("every AI action must be auditable") is not violated in the sense of missing data — but the specific claim "a scoring drift after a prompt change is always traceable to a specific version bump" is weaker than documented: it's traceable only if every future developer remembers the convention, with nothing catching a silent miss.

**Why Medium, not High/Critical:** this is a process-integrity gap, not an exploitable defect — the six existing prompt-version constants are all currently correct and match their prompt text (verified by reading each pair in this review). It does not let AI output reach a recruiter as falsely "verified/passing" (Critical bar) and is not itself an unvalidated live gap (High bar: nothing is exploited because prompt changes to date have all bumped correctly).

**Recommendation for a future wave:** either (a) add a lightweight test that hashes each `..._SYSTEM_PROMPT`/`..._PROMPT_VERSION` pair and fails if the hash changes without the version string changing, or (b) actually populate `ai_prompt_versions` on deploy and add the FK, matching the doc's original design. Left tracked, not fixed, per this wave's Medium/Low policy.

### Finding B (Medium) — Outreach-drafting and response-classification calls still never write a real `ai_runs` row, though the schema has supported it since Phase 11

`apps/web/lib/outreach/outreach-actions.ts`'s own module comment (lines 45-65) documents this as a **deliberate Phase 9 decision**: at the time, `ai_runs.workflow_type`'s CHECK constraint did not admit `outreach_draft_generation`/`response_classification`, so inserting a real row would have failed a constraint, and the file chose to leave `ai_run_id` `null` on both `outreach_messages` and `candidate_responses`, capturing the full AI-call record (model/prompt-version/tokens/cost/confidence) on the corresponding `audit_events` row's `metadata` instead — which does satisfy Core Principle #10, just via a different table.

**What has changed since, that the code comment does not reflect:** `supabase/migrations/0031_copilot.sql` (verified directly, lines 822-831) extended `ai_runs_workflow_type_check` to admit exactly `outreach_draft_generation` and `response_classification`, alongside `copilot_response`. Docs/09-ai-architecture.md §9.7 already flags this as a "schema-only fix" whose TypeScript-layer follow-up was explicitly deferred. **That follow-up still has not happened**: `outreach-actions.ts` still hardcodes `ai_run_id: null` at both insert sites (verified directly, lines 246 and 932), and its own comment's central claim — "Inserting a real ai_runs row... would therefore always fail its CHECK constraint" — is now factually stale.

**Impact:** every outreach draft and every response classification remains fully auditable (via `audit_events.metadata`), so no Core Principle #10 violation exists in substance. The gap is that the canonical `ai_runs` table — the one place docs/09-ai-architecture.md says "every AI call" lives, and the one a future AI-quality dashboard (§10.12) would query — is silently missing two of the platform's six AI workflows' rows, and a developer relying on `ai_runs` alone (rather than also joining `audit_events`) would undercount AI usage/cost for these two workflows.

**Why Medium, not High:** the audit data exists, just in a different table than expected — this is a completeness/consistency gap given another layer (`audit_events`) already covers the substantive requirement, matching this wave's own Medium rubric ("design gap with limited practical impact given other layers").

**Recommendation for a future wave:** update `outreach-actions.ts` to actually insert an `ai_runs` row for both workflows now that the CHECK constraint admits them, and correct the now-stale module comment. Left tracked, not fixed, per this wave's Medium/Low policy (this also touches migration-adjacent schema assumptions the brief asked not to be touched casually).

## Eval dataset — structure, location, version

**Location:** `apps/web/lib/ai/eval-fixtures/` (new this wave — no prior eval-fixtures directory existed; Phase 11's `lib/copilot/eval/` and Phase 6's `test/fixtures/candidate-documents/` are separate, pre-existing suites this one complements, not duplicates).

**Version:** `EVAL_FIXTURE_SET_VERSION = '1.0.0'` (`eval-fixtures/version.ts`), following the exact same semantic-version-string convention this codebase already uses for prompts (`REQUIREMENT_EXTRACTION_PROMPT_VERSION`, `COPILOT_PROMPT_VERSION`, etc.) — bump it whenever a fixture's content changes in a way that could change an existing assertion's expected result.

**Files:**

- `job-fixtures.ts` — 3 synthetic job descriptions (`Retail Store Manager`, `Regional Operations Manager`, `Assistant Store Manager, Food Service`), each with raw line-prefix JD text (for the real extraction orchestration) and an already-frozen `FrozenRequirement[]`/`TrustedMatchingRequirement[]` pair (for the matching workflow), varying mandatory/preferred mixes and including one embedded instruction-shaped ("ignore previous instructions...") `UNCLEAR:` line.
- `candidate-fixtures.ts` — 7 synthetic candidates (obviously fake names — "Alex Testworthy," "Jordan Failwright," "Taylor Injectionova," etc. — fictional companies, no real PII) across the 6 required scenarios: **clear pass**, **clear fail** (evidence directly contradicts a mandatory gate), **borderline** (conflicting/indirect evidence for a preferred criterion), **missing information** (zero evidence for a mandatory gate, distinct from the contradicted case), **prompt injection** (instruction-shaped text embedded in both CV text and an evidence-bundle item), and a **bias probe pair** (two structurally identical candidates differing only in a university-name signal).
- `eval-fixtures.test.ts` — 17 Vitest tests running the fixtures through: `runRequirementExtraction`/`runCandidateDocumentExtraction`/`runMatchingAssessment` (the real orchestration + deterministic test-double providers), `computeDeterministicMatchResult` (real `gates.ts`+`scoring.ts`, no AI), and `validateOutreachDraftEvidence` (real validator).

**What the tests assert, concretely:**

- The injection-attempt fixture's suspicious instruction text never leaks into a stored score/note/evidence field as if it were real evidence (both at the CV-parsing layer and the matching layer), and the embedded JD-side instruction is captured only as `requires_clarification`, never smuggled in as `mandatory`/`preferred`.
- The missing-information fixture surfaces as `insufficient_evidence`/`pending_verification` (matching) and `hasEvidence: false` with null value/excerpt/confidence (CV parsing) — never a fabricated value, and distinctly from the clear-fail fixture's genuine contradiction.
- The borderline-evidence fixture's conflicting/indirect evidence is confidence-discounted (`effectiveScore < rawScore`), never silently rounded up to a full-weight pass.
- The bias-probe pair produces byte-identical deterministic results (`eligibility`, `overallScore`, `evidenceCoveragePct`, every gate result) despite differing only in a university-name signal — proving the deterministic layer has no structural channel for that signal, with the explicit caveat (repeated in the test's own comment) that this says nothing about live-model behavior.

**A genuine fixture-authoring finding worth recording:** an early draft of the prompt-injection candidate fixture accidentally included the literal phrase "valid food safety certification" inside its injected instruction text. Because `TestMatchingAIProvider` matches evidence by case-insensitive substring of the requirement name (a deliberate simplification for a deterministic offline double, not a flaw in the real prompt design), that draft fixture's injected text was treated as genuine matching evidence and the gate resolved to `pass` — the test caught this immediately (`AssertionError: expected 'pass' not to be 'pass'`). This was a fixture-authoring bug, not a defect in `gates.ts`/`scoring.ts` themselves (those correctly trusted the assessment they were given, exactly per their contract — evaluating evidence _legitimacy_ is explicitly the AI-assist layer's job, not the deterministic layer's). It was fixed by rewording the fixture. It does illustrate a real, narrower structural point recorded here rather than as a separate numbered finding (impact assessed as none beyond documentation, since `lib/matching/evidence-bundle.ts` only ever admits verified/accepted candidate data into the evidence bundle in the first place — a raw, unreviewed instruction-shaped string could not reach this code path in production without a human first marking it "verified"): the deterministic gate layer's only defense against illegitimate evidence content is (a) the upstream verified-only evidence-bundle filter, and (b) the real model's own prompt-instructed judgment — `gates.ts` itself performs no independent content-legitimacy check, by design.
