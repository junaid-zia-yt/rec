**Build Phase 12 addition — durable job engine, inbound webhook processing, and notifications.** A request-triggered (no persistent worker) durable job engine (`lib/jobs/`) now backs every one of the above integrations' async work — retries with exponential backoff + jitter, dead-lettering, manual retry, idempotent enqueue, per-attempt audit trail. Inbound webhook handling (`lib/integrations/webhook/process-inbound-webhook.ts` + `signature-verification.ts`) is implemented and tested as a plain function against a fake Supabase client, covering duplicate-webhook dedup (DB-constraint-driven, not an app pre-check), all 3 documented signature schemes with deliberately tampered inputs, and the null-`external_event_id` case — **but the actual Next.js route handlers (`app/api/webhooks/<provider>/route.ts`) that would receive a real inbound HTTP webhook were never built this phase**; no live webhook can be received until those routes exist. ## 11.2 TA Tracker — Detailed Assessment

**[CONFIRMED — Technical Blocker]** The project instructions explicitly forbid inventing a TA Tracker API, and the MOM gives no technical detail about it beyond "proprietary/internal system." We have no evidence it exposes any API, export, or webhook. Until the client supplies one of: (a) API documentation, (b) direct read access to its database/export, or (c) a scheduled CSV/file export mechanism, **no TA Tracker integration work should be scheduled**, and no UI should claim a live sync. The Integrations screen should show TA Tracker as "Not connected — pending technical documentation from client" rather than omitting it, so the gap stays visible rather than silently dropped. **[CLIENT CONFIRM — blocks Phase 14, P0 for eventual parity with Dave's existing workflow, not for the POC itself]**.

**Build Phase 12 update — the non-API modes are no longer hypothetical.** CSV import/export mode (`lib/integrations/ta-tracker/csv-mode.ts`) and secure manual exchange mode (`manual-exchange-mode.ts`) are real, implemented, and unit-tested — they need no vendor API at all, only a file/export the client can already produce today. API mode remains, and will remain, `lib/integrations/ta-tracker/api-mode.ts`: a deliberate, permanent stub that takes no configuration and performs no I/O — `attemptApiModeSync()` can only ever return `status: 'no_documentation'`, structurally guaranteed both by that module (no branch exists that could return anything else — `api-mode.test.ts` confirms this across repeated calls) and by `integration_connections`' own DB CHECK constraint (a `provider='ta_tracker' AND mode='api'` row can never reach `status IN ('connected','sync_error','disconnected')` — pgverify TEST18h). `connectIntegrationAction` refuses a `mode='api'` connection attempt before it ever reaches that constraint, with an honest message pointing the caller at CSV/manual exchange instead. **Any future wave that receives real TA Tracker API documentation must replace `api-mode.ts` entirely, not extend it with a conditional branch** — that replacement is the intended signal that real API work is starting.

## 11.3 LinkedIn — Detailed Assessment

**[CONFIRMED]** The project instructions explicitly forbid automating LinkedIn in a way that violates its platform rules — this rules out scraping and automated messaging entirely, regardless of technical feasibility. What remains: a recruiter manually pastes/imports a LinkedIn profile URL or exported data into the platform, and manually sends LinkedIn messages outside the platform (or the platform opens a compose window/deep link, but does not send on the user's behalf via an unauthorized channel). **[CLIENT CONFIRM — blocks Phase 14]**: whose LinkedIn account is used for any agency-assisted outreach — this was asked in the discovery call and left unanswered (MOM §8), and it has real data-ownership and compliance implications (who owns the resulting connections/conversation history if the relationship ends).

## 11.4 Apollo — Detailed Assessment

**[CONFIRMED]** Apollo is already in active use by the client (MOM §3.2, ~83% cited hit rate — Dave's self-reported figure, not to be presented as a vendor SLA). Apollo publishes a documented REST API; a standard key-based integration is technically straightforward. **[CLIENT CONFIRM]** whether the agency provisions its own Apollo account/API key or uses the client's existing one — same ownership question as LinkedIn, and directly affects the Integrations screen's account-ownership field.

**Build Phase 12 update.** `lib/integrations/apollo/apollo-client.ts` (`RealApolloClient`) is a real, complete REST client against Apollo's documented People Match/Enrich endpoint — conservative placeholder rate-limit pacing (labelled as such, not a confirmed Apollo limit), a 15s request timeout, and four distinct typed failure kinds (`not_configured`, `rate_limited`, `invalid_request`, `provider_error`, `network`), each confirmed distinguishable and never silently swallowed by `apollo-client.test.ts` (mocked `fetch`, since no `APOLLO_API_KEY` is configured in this environment). `getApolloClient()`'s selector (`apollo-dev-adapter.ts`) refuses to construct the real client at all while unconfigured, throwing a typed `not_configured` error rather than ever returning fabricated contact data — confirmed by `apollo-dev-adapter.test.ts`. **Still, honestly, never exercised against a live Apollo account** — nothing here claims a tested integration until a real key is configured and a real call is made.

## 11.5 Email, SMS, Calendars

Email is the only outreach channel with zero blockers — it's in the approved stack (Resend) and requires no client account access. SMS needs a provider decision **[CLIENT CONFIRM]** since none is currently in the approved technology stack; Build Phase 12 built `lib/integrations/sms/adapter.ts`, a thin typed wrapper ready to plug a real provider behind once one is chosen, but it still has none — `connectIntegrationAction` refuses to ever report SMS as connected. Calendars are low-priority (interview scheduling is workflow #18 in the project description, not core to the POC); Build Phase 12 built real Google Calendar (`google-calendar-adapter.ts`) and Microsoft Calendar (`microsoft-calendar-adapter.ts`) adapters behind a shared `CalendarAdapter` interface, both structurally guarded to throw a typed `not_configured` error before any network call while their respective OAuth credentials are absent (confirmed by `selector.test.ts`) — neither has been exercised against a live account.

## 11.6 Compliance & Fallback Notes

For every integration: no integration is marked "working" in the UI or in any status report to the client until it has been configured with real credentials and tested against a live call — per the project instructions' explicit prohibition on claiming untested integrations work. Where an integration is blocked or unavailable, the corresponding workflow (e.g., outreach) must still function manually (draft/copy/paste), so the platform is never _fully_ blocked by an unresolved third-party integration. Build Phase 12's `integration_connections` table and `connectIntegrationAction` enforce this rule in code, not just in this document: a provider without configured credentials cannot be marked `connected` by any code path, and TA Tracker's `mode='api'` cannot reach `connected` at all, ever (DB CHECK-enforced — see §11.2).
