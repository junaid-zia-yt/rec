# 13 — API & Service Boundaries

## 13.1 Architecture Overview

```
┌─────────────┐     ┌──────────────┐
│  Web (Next)  │     │ Mobile (Expo) │
└──────┬───────┘     └──────┬───────┘
       │  Next.js Server Actions / Route Handlers (thin API layer)
       ▼
┌───────────────────────────────────────────────────────────┐
│ Domain Services (server-only)                              │
│  ├─ Recruitment domain service (projects/JDs/scorecards)   │
│  ├─ Candidate-scoring service (deterministic gates+formula)│
│  ├─ AI orchestration service (Claude calls, schema valid.) │
│  ├─ Document-processing pipeline (upload→parse→extract)    │
│  ├─ Notification service                                    │
│  ├─ Integration adapters (Apollo/Email/Calendar/TA Tracker*)│
│  ├─ Audit service (append-only writer)                     │
│  └─ Analytics service (read-model aggregation)              │
└───────────────────────────┬─────────────────────────────────┘
                             ▼
                  Supabase (Postgres + RLS, Auth, Storage, pgvector)
                             ▲
                  Background jobs (queue-driven: parsing, scoring, outreach send)
```

\* TA Tracker adapter does not exist yet — see [[11-integration-plan]].

## 13.2 Web vs. Mobile Responsibilities

**Web:** full authoring surface — JD upload, scorecard building, candidate pipeline management, outreach composition, admin/settings, audit log, analytics. **Mobile:** review-and-approval-first per the project description ("mobile review and approval application") — shortlist verification/sign-off, gate review, notifications, candidate dossier read view. Both share the same API layer and TypeScript types (generated from the Supabase schema + Zod schemas) so business rules are never duplicated.

## 13.3 Authentication Layer

Supabase Auth session → JWT with `organization_id`/`role` custom claims → verified in every Server Action/Route Handler via a shared `requireAuth(role[])` helper before any domain-service call.

## 13.5 Background Jobs

Queue-driven (Supabase's pg-based queueing or a lightweight worker on Vercel Cron/Edge, to be decided in Phase 1 engineering setup): document parsing, AI scoring runs, outreach sending, POC metric aggregation. All jobs are idempotent and re-triggerable, and every job's outcome writes an `AI_runs` and/or `audit_events` row so a stuck or failed background job is always visible to a human, not silently retried forever.

## 13.6 Notification Service

Fires on: pending review needed, gate failure needing attention, client decision received, outreach response received. Delivers in-app (`notifications` table + realtime subscription) and email (Resend), per user preference.

## 13.7 Analytics Service

Reads from `audit_events`, `AI_runs`, and `candidate_role_matches` to compute time-to-shortlist, gate-fail rate, evidence-completeness, and override rate — a read-model layer, not a separate data store, to avoid a second source of truth.

## 13.8 Mobile API Routes (Build Phase 13 Wave 1)

The architecture decision from §13.2 ("both share the same API layer") is now implemented: `apps/web/app/api/mobile/*` Route Handlers, bearer-token authenticated, reusing the exact same business-logic helpers, Zod schemas, permission gates and audit calls as their web Server Action counterparts. **Plain reads (lists/detail views) are NOT built here** — the mobile app queries Supabase directly with the user's JWT, RLS-protected identically to web. Only writes that carry business logic beyond a simple RLS-scoped insert/update are routed through this layer.

### Auth

Every route requires `Authorization: Bearer <supabase-access-token>` (the user's live Supabase session JWT — never a custom token). The token is verified server-side against Supabase (`auth.getUser()`) on every request; nothing is trusted from the token's own claims. A missing/invalid/expired token returns `401 { error: string, code: 'unauthorized' }`; a request made when this deployment has no Supabase project configured returns `401 { error: string, code: 'not_configured' }`. See `apps/web/lib/auth/mobile-session.ts` (`authenticateMobileRequest`) and `apps/web/lib/supabase/bearer.ts`.

Every route then passes that same bearer-scoped Supabase client into `apps/web/lib/auth/session.ts`'s `resolveActiveOrg` / `requireOrgMembership` / `requirePermission` (now accepting an optional injectable `client` as their last parameter — backward compatible; omitting it preserves the exact prior cookie-based behavior for every existing web call site) — so permission checks are byte-for-byte the same logic the web app uses, never re-implemented.

`revalidatePath(...)` calls present in the mirrored web Server Actions are intentionally omitted in every mobile route (a Next.js page-cache primitive with no meaning for a JSON API) — each omission is marked with a comment in that mirrored web action's own header, not repeated per route here.

### Not built this wave (scope note for the parallel mobile-app wave)

- **`startCopilotConversationAction`** has no mobile route yet — `/api/mobile/copilot/turn` requires an existing `conversationId`. A future `POST /api/mobile/copilot/conversations` route mirroring it is straightforward to add on the same pattern but was out of scope for this wave's explicit route list. **Re-verified at the end of Build Phase 13 (Wave 6):** this gap is still open — `apps/web/app/api/mobile/copilot/` contains only `turn/route.ts`, no `conversations/` route, and `apps/mobile/lib/api/client.ts` has no wrapper for starting a conversation from mobile. `apps/mobile/screens/home/CopilotConversationWorkspaceScreen.tsx` (Wave 3) works around this by requiring a `conversationId` route param — the mobile app has no "start a new copilot conversation" entry point of its own; a conversation must already exist (e.g. started on web) before it can be opened on mobile. Flagged again here, not silently carried forward, per [[build-phase-13-report]]'s known-limitations section.
- **`sendShortlistToClientAction`** (internally_approved → sent_to_client) has no mobile route — the brief's route list asked only for internal approval and the client's own decision, not the recruiter-side "send to client" action; flagged in case the mobile app's shortlist workflow expects it.
- **`manuallyRetryJobAction`** was explicitly out of scope per the brief.
- Read/list endpoints (candidate lists, shortlist details, notification feed, conversation history, etc.) are deliberately NOT built here — per the architecture decision, the mobile app queries Supabase directly (RLS-protected) for those.
