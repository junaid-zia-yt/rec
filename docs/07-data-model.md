# 07 — Data Architecture

All tables carry `id uuid pk default gen_random_uuid()`, `created_at`, `updated_at`, and (except `organizations` itself and cross-org platform tables) `organization_id uuid not null references organizations(id)`. RLS policy convention: `USING (organization_id = current_org_id())` on every tenant table, enforced via a Supabase auth JWT claim set at login/org-switch.

## 7.3 Tenant Isolation Strategy

Every tenant table carries `organization_id`. RLS policies use a `current_org_id()` function reading a custom JWT claim set at sign-in/org-switch (Supabase Auth custom claims). Platform Admin bypasses via a `service_role`-gated admin API only, never via a client-exposed policy relaxation. Client Decision-Maker access is **not** organization membership — it is a separate, narrower policy keyed to `shortlist_candidates` rows explicitly shared with their `client_id`, so they never get org-wide visibility even by mistake. Build Phase 4 extends this same narrowing to scorecard approval specifically: a Client Decision-Maker's `scorecard_approvals` insert additionally requires `recruitment_projects.client_can_approve_scorecards = true` for that project — an explicit, per-project opt-in on top of tenant scoping, never a broadening of it (docs/06-roles-permissions.md §6.2.2).

Build Phase 5 adds `public.can_access_candidate(target_candidate uuid)` (`supabase/migrations/0021`), a single `SECURITY DEFINER` helper every `candidate_*` table's recruiter/client policy calls, so the visibility rule is defined once rather than re-derived per table: org-wide for `agency_admin`/`read_only_reviewer`/`platform_admin`; a candidate the recruiter sourced (`created_by`) or that has a `candidate_project_entries` row for a project they're assigned to (`is_assigned_to_project()`, reused unchanged from Build Phase 3) for `recruiter`; and, for `client_decision_maker`, only a candidate with a `candidate_project_entries` row that is **both** `client_visible = true` **and** for a project belonging to their own `client_id` — the brief's "shortlisted or explicitly shared candidates" rule (§PRIVACY), enforced in the database rather than trusted to application code alone. Verified functionally (not just reviewed) against a real Postgres instance with `SET ROLE authenticated` + JWT-claim role-switching, including cross-organization denial — see docs/build-phase-5-report.md.

RLS is row-level only — it can allow or deny a whole row, never reshape or redact a column. Two Build Phase 5 requirements fall outside what RLS can do and are therefore application-layer concerns, both centralized in `apps/web/lib/candidates/visibility.ts` so every screen and server action applies them identically: masking a candidate's contact values for roles outside `platform_admin`/`agency_admin`/`recruiter`, and omitting `candidate_profiles.recruiter_notes` entirely (not nulling it) from any payload built for a role that shouldn't see it.

## 7.4 Candidate Deduplication Strategy

**Implemented differently from this section's original plan, recorded here for accuracy.** The original plan called for pgvector similarity on a name+work-history embedding for fuzzy matches; Build Phase 5 implements the deterministic first pass as planned (normalized email/phone exact match, plus document checksum) but replaces the embedding-based fuzzy pass with a configurable, dependency-free token-overlap (Jaccard) heuristic over name/company/location (`apps/web/lib/candidates/dedup.ts`, `DEFAULT_DEDUP_CONFIG`: `fuzzyThreshold: 0.6`, weighted 0.6/0.25/0.15 name/company/location) — no embedding model call, no pgvector column on `candidates` yet. This was a scope decision for this build phase, not an oversight: pgvector-based fuzzy matching remains a reasonable future upgrade once AI CV parsing (also out of scope this phase) gives richer profile text to embed against, and swapping the heuristic for it later requires no schema change to the suggestion consumers (`DuplicateCandidateSuggestion`, `apps/web/components/domain/candidates/duplicate-resolution-panel.tsx`).

Whatever the matching method, the result is always a **suggestion**, never auto-merged, consistent with Core Principle #6 (never silently alter candidate data). A confirmed merge is the recruiter's explicit decision (`mergeCandidatesAction`, `apps/web/lib/candidates/merge-actions.ts`), writes an `audit_events` row, and keeps the losing record's id and row (`candidates.status = 'merged'`, `merged_into_candidate_id`) as a resolvable alias rather than deleting it — never a destructive automatic merge. Known limitation, reported honestly rather than glossed over: the reassignment of the losing candidate's child rows is a sequence of ordinary Supabase calls, not one atomic Postgres transaction, so a mid-sequence failure could leave a merge partially applied; a follow-up phase should move this into a single Postgres RPC function for true atomicity.

## 7.5 Document Versioning Strategy

`candidate_documents.version_no` increments per re-upload; prior versions are retained (soft state `superseded`, not deleted) so evidence citations from an old score remain resolvable even after a newer CV is uploaded. A `requirement_evidence` row always references a specific `candidate_documents` version, not "the current CV." Build Phase 5 implements this by having `candidate_documents` reference the shared `document_uploads` table (Build Phase 3, `0011`) rather than storing file metadata itself — `document_uploads` already anticipated a `'candidate_document'` owner_type, so checksum/MIME/size/private-storage-path bookkeeping is centralized there and reused, not duplicated. The same versioning pattern now governs scorecards (Build Phase 4): `scorecard_versions.requirement_snapshot` freezes exactly which requirements/weights were in effect at approval time, so a `candidate_role_matches.scorecard_version_id` reference always resolves to the rules that were actually used, even after the scorecard is later edited into a new draft version.

## 7.6 Soft-Deletion Strategy

No hard deletes on `candidates`, `candidate_documents`, `audit_events`, `ai_runs`, or anything the audit trail depends on. Soft delete via `deleted_at` + RLS exclusion from default queries. Hard delete is reserved for explicit candidate data-deletion requests ([[12-security-compliance]]) and is itself an audited action. `job_requirements` is the one exception noted in Build Phase 4: a requirement may be hard-deleted by a recruiter/agency admin while still in `draft`/`proposed` review (never after it has been captured into an approved `scorecard_versions.requirement_snapshot`, which is immutable and unaffected by a later requirement deletion).

Build Phase 5 implements the candidate half of this honestly and only partially: `archiveCandidateAction` sets `candidates.status = 'archived'` (row and history kept, hidden from active views), and `requestCandidateDeletionAction` durably **records** a deletion request (`candidates.status = 'deletion_requested'` plus `candidate_consents.deletion_requested/_at/_by/_reason`) — but does not itself erase any data. Actually fulfilling a deletion request is deliberately left for a later, explicitly audited admin action once a data-retention policy exists (a business decision this build phase does not make; see docs/build-phase-5-report.md's blockers). `candidates.deleted_at` exists in the schema but is reserved, never set by this phase's code.

## 7.7 Audit-Event Strategy

`audit_events` is append-only (revoke UPDATE/DELETE grants at the database role level, not just application logic). Every state-changing service-layer call wraps its business write and its `audit_events` insert in one transaction — no code path can commit one without the other. Build Phase 4 adds `requirement.*` and `scorecard.*` action names (`apps/web/lib/audit/log.ts`) and, for `ai_runs` specifically, append-only is enforced the same way `audit_events` and `scorecard_approvals` are: `REVOKE UPDATE, DELETE` at the database-role level, not RLS alone. Build Phase 5 adds `candidate.*` action names (created/updated/archived/deletion_requested/merged/document_uploaded/document_rejected/experience__/education__/certification__/skill__/assigned_to_project/stage_transitioned/csv_imported/csv_import_row_failed) and applies the same append-only DB-role revoke to the new `candidate_pipeline_events` table specifically, so a pipeline-stage history can never be edited or deleted even by a compromised application role — only added to.

## 7.8 AI CV-Parsing Strategy (Build Phase 6)

**Idempotency.** `candidate_document_processing_jobs.idempotency_key` (`<candidate_document_id>:<attempt_no>`, unique) plus a partial unique index on `candidate_document_id` limited to the genuinely active statuses (`queued`, `extracting_text`, `parsing` — narrowed from an initial, over-broad set in `0025` after review: a job resting at `needs_ocr` or `awaiting_review` is stopped and waiting on a human, not doing active work, so it must not block a reprocess attempt) guarantee at most one concurrent processing attempt per document.

**Evidence-unknown invariant, enforced twice.** The brief's "If evidence is absent, return unknown" rule is enforced at both the AI-output-validation layer (`CandidateExtractionOutputSchema`'s `extractedScalarField()` `.refine()`, `packages/types/src/index.ts`) and, independently, at the database layer (`candidate_extracted_fields_unknown_shape` CHECK constraint, `0022`) — a partial/guessed value can never be persisted even if a future code change accidentally bypassed the Zod check, and never validated even if a future change bypassed the DB check.

**Apply-without-destroying.** Accepting a verified/edited field (`acceptAllVerifiedFieldsAction`, `apps/web/lib/candidates/document-processing-actions.ts`) writes only into `candidates`/`candidate_profiles`/`candidate_contact_points`/`candidate_experiences`/`candidate_education`/`candidate_certifications`/`candidate_skills` and stamps `candidate_extracted_fields.applied_at` — the source `candidate_documents` row and its underlying Storage file are never written to by this pipeline (brief §AI PIPELINE step 10). `compensation`/`availability` scalar fields deliberately never auto-write into `candidate_profiles`' structured `compensation_min/max`/`availability_date` columns (a recruiter's own deliberate range/date entry) — they land in the new free-text `compensation_notes`/`availability_notes` columns instead, visible next to the structured field rather than silently overwriting it.

**Permission-matrix interpretation, recorded explicitly** (same convention as §6.2.2's client-approval opt-in): every write action in `document-processing-actions.ts` is gated on the `candidate_documents` resource (`agency_admin`/`recruiter`: full), not `candidate_evidence` (`agency_admin`/`recruiter`: read-only in the matrix, since that resource represents AI-authored content). Kicking off/reprocessing/reviewing a document's AI output is a human action performed on the document-processing pipeline — the same category the matrix already grants full access to via `candidate_documents` — not an attempt by a human to "create" evidence text. Migration `0022`'s RLS write policies encode the identical interpretation at the database layer. See docs/build-phase-6-report.md for the full reasoning.

## 7.9 Candidate Matching Strategy (Build Phase 7)

**Seven new tables** (`supabase/migrations/0027`), implementing docs/08-candidate-scoring.md end to end: `matching_runs` (append-only, one row per evaluation attempt — the same job-row convention as Build Phase 6's `candidate_document_processing_jobs`), `candidate_role_matches` (the mutable current-state projection every other screen reads, always pointing at its `latest_matching_run_id`), `mandatory_gate_results`, `requirement_evidence`, `scoring_breakdowns`, `human_reviews`, and `review_decisions`. `candidate_role_matches` finally supersedes the "not yet built" placeholder §7.1 carried since Build Phase 5.

**Run-history vs. current-state split.** Every recalculation (scorecard re-approved, document re-uploaded, manual re-score — docs/08-candidate-scoring.md §8.8) inserts a new `matching_runs` row and a fresh set of child `mandatory_gate_results`/`requirement_evidence`/`scoring_breakdowns` rows; nothing is ever overwritten in place. `candidate_role_matches` is the one row per (candidate, job) that the UI actually reads, updated to point at the newest run — so history stays fully inspectable while the "current" query stays a single-row lookup.

**Score-only-when-eligible, enforced twice.** `candidate_role_matches.overall_score` is null whenever `eligibility <> 'eligible'` — a failed or unresolved mandatory gate excludes the candidate from ranked output by construction (docs/08-candidate-scoring.md §8.3), enforced both in the deterministic scoring code (`apps/web/lib/matching/evaluate.ts`) and independently by the `candidate_role_matches_score_only_when_eligible` CHECK constraint at the database layer.

**Human override, enforced as a full record or not at all.** `mandatory_gate_results` carries `deterministic_result` (the immutable rule outcome) separately from `state` (the brief's five displayed states, including `human_override`). The `mandatory_gate_results_override_requires_full_record` CHECK constraint requires `override_result`, `override_by`, `override_reason`, `override_evidence_note`, and `override_at` to all be present together whenever `state = 'human_override'` — a partial override record can never be persisted even if application code has a bug.

**Configurable quality thresholds.** `0027` adds nullable `scorecards.ranked_consideration_threshold_pct` / `.preferred_shortlist_threshold_pct` overrides; a null falls back to `DEFAULT_RANKED_CONSIDERATION_THRESHOLD_PCT` (90) / `DEFAULT_PREFERRED_SHORTLIST_THRESHOLD_PCT` (95) in `packages/types`, resolved in exactly one place (`apps/web/lib/matching/thresholds.ts`) rather than inlined anywhere in scoring logic (docs/10-ai-evaluation-guardrails.md §10.13).

**`ai_runs`/`ai_prompt_versions` workflow_type extended.** Both tables' CHECK constraints now additionally admit `'candidate_matching'`, alongside the existing `'requirement_extraction'`/`'candidate_document_extraction'` values (same drop-and-recreate pattern Build Phase 6's `0026` used for `error_kind`).

**Client Decision-Maker has no access to any of the seven new tables** — see docs/06-roles-permissions.md §6.2.5 for the reasoning; a client-facing shortlist/comparison view is explicitly deferred to a future Shortlist phase.

## 7.10 Human Review and Shortlisting Strategy (Build Phase 8)

**Six new tables** (`supabase/migrations/0028`), implementing docs/08-candidate-scoring.md §8.10 end to end and closing the deferral §7.9 named: `verification_requests`, `shortlists`, `shortlist_versions`, `shortlist_candidates`, `client_decisions`, `shortlist_activity`. Two Build Phase 7 tables are extended in place: `human_reviews.decision` gains `escalated`/`note_added`, `candidate_role_matches.review_status` gains `escalated`. `candidate_project_entries` gains a lightweight "Candidate Interest Confirmed" tri-state (`interest_status`/`interest_confirmed_by`/`interest_confirmed_at`/`interest_note`) — the pipeline-stage table remains the established home for candidate-journey state (docs/build-phase-5-report.md) rather than a new table.

**`shortlists` and `shortlist_candidates` are rebuilt, not just extended.** The original §7.1 placeholder shape (`shortlists.status: draft/submitted/decided`, a flat `shortlist_candidates` join) predates the brief's full workflow (Proposed Shortlist → Internal Approval → Client Review → Accepted/Discuss/Rejected) and Build Phase 7's `candidate_role_matches`/`matching_runs` entities it must now reference. `0028` replaces both tables' shape entirely rather than layering a second, parallel pair alongside the old one.

**Header/version split, same pattern as `scorecards`/`scorecard_versions`.** `shortlists` is the mutable "current state" row (status, override authorization, pointer to the current version); `shortlist_versions` is the immutable-once-submitted snapshot, so a `client_decisions` row always points at a fixed, unchangeable candidate set even if the recruiter later rebuilds the shortlist after a `discuss`/`rejected` outcome. A rebuild is a new `version_number`, never an edit to a decided-on version.

**Two cross-row rules a CHECK constraint cannot express, enforced by a BEFORE INSERT trigger instead.** `enforce_shortlist_candidate_rules()` on `shortlist_candidates` rejects (a) a candidate whose `candidate_role_matches.eligibility <> 'eligible'` — the brief's "never rank failed mandatory-gate candidates" applied again at the shortlist-build boundary, not just the quality-review queue view (`apps/web/lib/shortlists/queue.ts`'s `filterRankable`) — and (b) a candidate that would push the version's row count past `shortlists.max_candidates` (default 3) without `shortlists.override_max_candidates = true`, itself only settable together with `override_by`+`override_reason` (`shortlists_override_requires_reason` CHECK). Duplicate inclusion is instead a plain `unique(shortlist_version_id, candidate_id)` constraint, since it needs no cross-table read.

**Client visibility gate is a compound status check, not a single flag.** A `client_decision_maker` sees a `shortlists`/`shortlist_versions`/`shortlist_candidates`/`shortlist_activity` row only once the parent shortlist has actually reached them (`status ∈ {sent_to_client, accepted, discuss, rejected}`) **and** it is their own `client_id` — `draft`/`pending_internal_approval`/`internally_approved` are never visible, matching the brief's "no candidate may be submitted to an end client without human approval" (Core Principle #8). `shortlist_activity` additionally requires `client_visible = true` per row, since internal recruiter reasoning/override rationale must never reach the client even once the shortlist itself is shared (docs/06-roles-permissions.md §6.2.6).

**Permission-matrix `'approve'` action, recorded explicitly (self-correction during this build).** §6.2's "Shortlists: A (approve/reject)" for Client Decision-Maker maps to the permission matrix's `'approve'` **action**, which `packages/types/src/permissions.ts`'s `hasPermission()` deliberately excludes from Agency Admin's/Recruiter's `'full'` level (`case 'full': return action !== 'approve'`). This was caught during this build: internal-approval and send-to-client actions are therefore gated on `'update'`, not `'approve'` — `'approve'` is reserved exclusively for `recordClientDecisionAction`, the client's own Accept/Discuss/Reject write. See docs/06-roles-permissions.md §6.2.6.

## 7.11 Outreach Strategy (Build Phase 9)

**Seven new tables** (`supabase/migrations/0029`), plus one extended table, implementing docs/09-ai-architecture.md workflows #14/#15 and the brief's "Outreach" spec end to end: `communication_preferences`, `outreach_templates`, `outreach_sequences`, `outreach_messages`, `outreach_approvals`, `communication_events`, `candidate_responses`. `candidate_contact_points` (Build Phase 5) gains `verified`/`verified_at`/`verified_by`. `outreach_sequences`/`outreach_messages`/`candidate_responses` **replace** the original §7.1 placeholder shape entirely (which sketched a single flat `outreach_contacts` table and a simpler `outreach_messages.status: draft/approved/sent/failed`) — the same "rebuilt, not layered" pattern §7.9/§7.10 used for `candidate_role_matches` and `shortlists`.

**The approval gate and the opt-out gate are both database triggers, not just application checks.** Two BEFORE triggers on `outreach_messages` are the actual hard enforcement of Core Principle #3/#8 ("no candidate may be submitted... without human approval") and brief functional requirement #10 ("AI classification must be reviewable and must not override opt-out rules"): one rejects any transition into `approved`/`scheduled`/`sent`/`delivered`/`responded` unless a prior `outreach_approvals` row with `decision = 'approved'` already exists for that message; the other rejects creating or advancing a message toward sending for a candidate+channel currently `opted_out` in `communication_preferences`. `apps/web/lib/outreach/status-transitions.ts` (the 9-state legal-transition graph) and `apps/web/lib/outreach/opt-out.ts` (`checkOutreachOptOutGate`) are application-level **pre-checks** that mirror these triggers exactly so a disallowed action gets a clear message instead of a raw Postgres error — the database trigger, not the pre-check, remains the actual authority, and if the two ever disagree the trigger wins (both files' own module comments say so explicitly).

**Idempotent sending.** `outreach_messages.idempotency_key` (`<outreach_message_id>:<attempt_no>`, `apps/web/lib/outreach/idempotency.ts`) plus a `(organization_id, idempotency_key)` unique index guarantee a retried send attempt with the same key is rejected at the database layer, not just detected in application code — pgverify TEST15c confirms this directly.

**Unsupported-claims prevention is deterministic, not AI self-report.** `outreach_messages.personalization_evidence` records which real, already-verified candidate evidence backed a draft's personalized claims (brief functional requirement #2/#5) — but the AI's own citation of that evidence is never trusted blindly. `apps/web/lib/outreach/unsupported-claims.ts`'s `validateOutreachDraftEvidence()` deterministically re-checks every citation against the candidate's real evidence bundle (same bundle Build Phase 7's matching workflow uses) before a draft is ever persisted or shown as evidence-backed; a citation that fails is stripped, never silently kept. See docs/09-ai-architecture.md §9.7 for the full AI-workflow detail.

**Response classification: AI suggests, only a human confirms, only a confirmation can gate.** `candidate_responses.ai_suggested_classification` is advisory only; `confirmed_classification` (human-set, requires `reviewed_by`+`reviewed_at` together, CHECK) is the sole authoritative value, and a database trigger (`apply_confirmed_opt_out_classification`) reads **only** that confirmed field to cascade a `'opt_out'` classification into `communication_preferences` — an unreviewed AI opt-out suggestion can never by itself block outreach (pgverify TEST15h confirms both halves: no cascade on an unconfirmed suggestion, a real cascade once confirmed).

**The `ai_runs` gap — schema-fixed in Build Phase 11.** `ai_runs.workflow_type`'s CHECK constraint was not extended by `0029` to admit an outreach-drafting or response-classification workflow type (this wave's brief forbade migration changes), so `outreach_messages.ai_run_id`/`candidate_responses.ai_run_id` were `null` for every row written under Build Phase 9/10. Build Phase 11's `0031_copilot.sql` — already touching this exact constraint to admit a `'copilot'` workflow type — added both missing values alongside it, closing the schema half of the gap; pre-existing `null` rows are not backfilled, and updating `apps/web/lib/outreach/*.ts` to actually insert a real `ai_runs` row on future runs remains an application-layer follow-up. See docs/09-ai-architecture.md §9.7 for the full reasoning.

**Channel reality, recorded honestly (no automation claimed where none exists).** Email is the only channel with a real send path (`apps/web/lib/outreach/channels/email.ts`, Resend-backed, untested against a live call in this environment — docs/11-integration-plan.md §11.5). LinkedIn is manual-only by design (per the project instructions' explicit prohibition on unsafe LinkedIn automation) — `apps/web/lib/outreach/channels/linkedin.ts` only ever builds a record of a send/response a recruiter performed themselves outside the platform, never an automated send() call. Phone/SMS follow the same manual-logging path as LinkedIn; no SMS provider is in the approved stack (docs/11-integration-plan.md §11.1/§11.5).

**Client Decision-Maker has no access to any of the seven new tables** — pgverify TEST15o confirms this at the database layer, consistent with §6.2.6's exclusion of Client Decision-Maker from Build Phase 7/8's recruiter-internal tables; outreach drafting/sending/response-handling is an internal recruiter workflow the client never sees.

## 7.12 Recruiter AI Copilot Strategy (Build Phase 11)

**Four new tables** (`supabase/migrations/0031_copilot.sql`), implementing docs/09-ai-architecture.md §9.2 workflow #17 ("Recruiter copilot... advisory, cites its sources... cannot answer -> says so, never fabricates a citation") end to end: `copilot_conversations`, `copilot_messages`, `copilot_tool_calls`, `copilot_usage_counters`. The governing brief's MUST-NOT list (never the final hiring decision, never an unconfirmed candidate-record mutation, never a mandatory-gate override, never an outreach approval, never a shortlist submission, never cross-tenant data, never a hidden recruiter note to a client, never invented evidence) is enforced at multiple independent layers rather than any single one — see docs/10-ai-evaluation-guardrails.md §10.14 for the full layering statement and docs/build-phase-11-report.md for the complete build/verification record.

**Scope snapshot, not live lookup — deliberately, and re-checked every turn.** `copilot_conversations.role_at_creation`/`client_id`/`recruitment_project_id`/`data_classification` are captured once at INSERT and made immutable by a trigger; a user's role, project assignment, or client membership can change after a conversation starts, so this snapshot alone is never trusted as still-current authorization. Every turn (`run-copilot-turn.ts`) independently re-loads the caller's **live** role/org/assignment state and denies with `status: 'permission_narrowed_since_conversation_start'` if it no longer matches what the conversation needs — a snapshot that has since become too broad relative to the live role is caught on the very next message, never silently honored.

**`client_decision_maker` conversations are structurally narrowed, not just permission-filtered.** A CHECK constraint forces `data_classification = 'restricted_notes_excluded'` (never `'standard'`) whenever `role_at_creation = 'client_decision_maker'`, and forces exactly one `recruitment_project_id` and one `client_id` (never org-wide) for the same role — narrowing the retrieval surface at the schema level before any application code runs at all.

**Tool-name allowlisting is enforced twice, independently, at two different layers.** `copilot_tool_calls.tool_name` carries a CHECK constraint admitting exactly the 13 tool names `apps/web/lib/copilot/tool-registry.ts`'s `TOOL_REGISTRY` also hard-codes as its only keys (`eval/gate-override-attempts.test.ts` asserts the two lists match exactly, catching drift either direction) — a tool call for any other name is rejected by Postgres even if application code somehow tried to record one. All 13 registered tools are read/summarize/explain/compare/draft/suggest only; `requiresConfirmation: false` on every one, since none of them writes to a candidate/job/scorecard/shortlist/outreach record at all (`apps/web/lib/copilot/gate-override-guard.ts`'s `FORBIDDEN_COPILOT_WRITE_TARGETS` names every mutation path a tool handler must never import or call — `gate-override-attempts.test.ts` greps every `tools/*.ts` handler file for a literal Supabase `.update(`/`.insert(`/`.upsert(`/`.delete(` call and fails the build if one is ever added). `copilot_tool_calls.requires_confirmation`/`confirmed_at`/`confirmed_by` exist in the schema as scaffolding for a future mutating tool this wave does not add — inert today, not yet load-bearing.

**Resource ownership is validated and recorded on every tool call, not merely assumed from RLS.** `apps/web/lib/copilot/resource-ownership.ts`'s `assertResourceOwnership()` re-checks the caller's organization/role/client scope against the actual row a tool call addresses before any handler runs, and `copilot_tool_calls.resource_ownership_validated` persists whether that check passed as an auditable fact, not a trusted claim — `eval/cross-tenant-extraction.test.ts` and `eval/candidate-comparison-integrity.test.ts` both exercise this against a resource id belonging to a different organization, a different client, and a different shortlist/job.

**Field-level redaction happens before any tool output can reach a prompt, never after.** RLS is row-level only and cannot redact a single column (the same limitation §7.3/§6.2.3 already documented for `candidate_profiles.recruiter_notes`); `apps/web/lib/copilot/redaction.ts`'s `redactForClassification()` strips `candidate_profiles.recruiter_notes`, `shortlist_candidates.recruiter_note`, and `human_reviews`-derived reviewer notes **entirely** (delete, never null) from any record a `restricted_notes_excluded` conversation's tool output could carry, before the orchestration layer ever assembles a prompt. `eval/hidden-note-leakage.test.ts` proves this holds even against a worst-case "model" that echoes a tool's entire raw result verbatim into its answer — the leak-proof property comes from the redaction happening inside the tool handler itself, never from trusting the model to behave.

**Unsupported claims are stripped by a deterministic guardrail, never trusted from the model's own citation.** `apps/web/lib/copilot/evidence-guardrail.ts`'s `validateCopilotEvidenceCitations()` re-checks every claim's citation against the set of records a tool call actually returned this turn — a fabricated id, or a real id with a paraphrased/fabricated excerpt, is stripped and the response gets a visible "could not be verified" caveat rather than a silently cleaned answer; `eval/unsupported-claims.test.ts` and `eval/prompt-injection.test.ts` both confirm the strip happens even when the fabrication is framed as system-level "authority" text injected into a legitimately-retrieved record.

**Persisted rate limiting, not an in-memory limiter.** `copilot_usage_counters` (one row per org/user/day) is the auditable source of truth for the daily message count (200/day) and cost cap ($5/day) — chosen over in-memory state because this is a serverless/Vercel deployment where in-memory state does not survive a cold start or span instances (docs/17-deployment-operations.md). Both constants are **placeholders pending a real product decision**, not calibrated numbers — recorded honestly in docs/build-phase-11-report.md rather than presented as tuned. `eval/cost-latency-thresholds.test.ts` spies on the provider directly to confirm it is never even called once either cap is already met, and confirms a runaway turn is bounded by both a hard 45-second wall-clock timeout and a hard 8-tool-call-iteration cap, with clean, resolvable DB state left behind either way (no row ever stuck "in progress").

**Every candidate-facing table this wave's tools read remains read-only from the copilot's perspective** — `mandatory_gate_results`/`candidate_role_matches` are read (to display already-computed eligibility/scores) but never written by any tool handler; the gate-override guard's grep explicitly treats a legitimate read of these tables as non-offending, only a write chain as an offense.

## 7.13 Integrations, Jobs & Notifications Strategy (Build Phase 12)

**Five new tables** (`supabase/migrations/0032_integrations_jobs_notifications.sql`): `background_jobs`, `integration_connections`, `webhook_events`, `notifications`, `notification_preferences` — the durable-jobs/integration-reliability/notification layer for docs/11-integration-plan.md's integrations and docs/09-ai-architecture.md's async workflows. Full build/verification record: docs/build-phase-12-report.md.

**`background_jobs` — request-triggered claim/execute, not a persistent worker.** There is no queue broker or worker process in this Vercel serverless deployment — a job is "claimed" by a single optimistic `UPDATE ... WHERE status = 'queued'` (`apps/web/lib/jobs/executor.ts`'s `executeJob`), which Postgres guarantees only one concurrent caller can win for the same row (confirmed by `executor.test.ts`'s simulated-concurrent-claim test), but which provides **no** heartbeat or lease: a claimed row that crashes mid-handler is left `running` forever with nothing to reclaim it. Failure handling is deterministic: `attempt_count >= max_attempts` dead-letters, otherwise the job is requeued with an exponential-backoff-plus-full-jitter delay (`lib/jobs/backoff.ts`); a `platform_admin`/`agency_admin` can manually retry a `dead_lettered` or `failed` job (`lib/jobs/manual-retry.ts`), which resets `attempt_count` to 0 for a fresh budget (a documented, deliberate tradeoff — see that file's header note) and is itself audited. Every job carries a `correlation_id` shared across its own `job.*` audit-event rows (`entity_id`, not the job's own id) so one job's full lifecycle is one query. Idempotent enqueue is keyed on `(organization_id, job_type, idempotency_key)` — a duplicate enqueue (a webhook retry, a UI double-submit) returns the existing row rather than inserting a second one.

**`integration_connections` — the TA-Tracker-API-mode-honesty CHECK, enforced twice.** A CHECK constraint makes it structurally impossible for a `provider = 'ta_tracker' AND mode = 'api'` row to ever reach `status IN ('connected', 'sync_error', 'disconnected')` — pgverify TEST18h proves this at the database layer, and `lib/integrations/ta-tracker/api-mode.ts`'s `attemptApiModeSync()` mirrors the same guarantee in application code (it takes no parameters, performs no I/O, and can only ever return `'no_documentation'` — `api-mode.test.ts` asserts this holds across repeated calls, not just once). CSV import/export and secure manual exchange are the only real TA Tracker connection modes. Apollo/Google Calendar/Microsoft Calendar connect only when real credentials are configured (`lib/env.ts`'s `*Configured` flags); none are configured in this environment, so none has been exercised against a live call. RLS grants write only to `agency_admin`, read to `agency_admin`/`platform_admin` (oversight) — no role but those two has any DB-layer access at all, including `client_decision_maker`, matched exactly by `resource-link.ts`'s deep-link check for this resource type.

**`webhook_events` — dedup via the DB unique constraint, never an application pre-check.** `(provider, external_event_id)` is UNIQUE with `external_event_id IS NOT NULL` excluded from the index (nulls never collide) — `lib/integrations/webhook/process-inbound-webhook.ts` relies on catching Postgres's own `23505` unique-violation rather than racing a SELECT-then-INSERT, confirmed at both layers: pgverify TEST18b (SQL-level) and `process-inbound-webhook.test.ts` (function-level, including the null-`external_event_id` non-false-positive case). No client-writable RLS grant exists for `authenticated`/`anon` at all — a real webhook route (not yet built, see §17.7) must use a service-role client. Signature verification (`signature-verification.ts`) is per-provider-scheme (generic HMAC-SHA256 for Apollo, Google's channel-token comparison, Microsoft's clientState comparison) and none has been exercised against a live-signed webhook — every scheme is structurally correct against public documentation only.

**`notifications` — permission-safe deep links, resolved fresh at render time, never stored.** No `action_url` column exists by design; `lib/notifications/resource-link.ts`'s `buildPermissionSafeDeepLink()` re-validates the _current_ viewer's access to `(resource_type, resource_id)` every time it is called (all 7 kinds: `scorecard_version`, `candidate_role_match`, `outreach_message`, `shortlist`, `poc_benchmark`, `verification_request`, `integration_connection`) and returns `{accessible: false}` — never a stale/blind URL — the instant a notification's resource is deleted, cross-tenant, or the viewer's own access has since been revoked (`resource-link.test.ts` proves the revoked-since-creation case explicitly). RLS is own-recipient-only, and `read_at` is the only column a client can ever mutate (`notifications_read_only_mutation` trigger rejects any other change — pgverify TEST18d). All 8 allowlisted `event_type` values have a corresponding trigger function (`lib/notifications/event-triggers.ts`) that resolves recipients strictly within the calling organization and enqueues via `background_jobs` (never a direct table write), each keyed for idempotent dedup as `<eventType>:<resourceId>:<recipientUserId>[:<dedupeSuffix>]`.
