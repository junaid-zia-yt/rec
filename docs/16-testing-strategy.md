## 16.1 Critical End-to-End Journeys

1. **JD → requirements → scorecard approval** (recruiter uploads JD, reviews AI-extracted requirements, builds scorecard, agency admin approves).
2. **Candidate import → gate evaluation → evidence review** (CV uploaded, parsed, mandatory gates evaluated, a failed-gate candidate is provably excluded from the ranked pool).
3. **Scoring → human review/override → shortlist finalization** (the sticky "Continue to Shortlist" action from the confirmed screenshot, including the ≤3-candidate soft-check and the gate-failure hard-block).
4. **Client decision** (Client Decision-Maker logs in via scoped link, sees only their shortlist, approves/rejects with comment, cannot see any other project).
5. **Outreach draft → approval → send → response capture** (nothing sends without an approval action).
6. **Full audit trail replay** (every action in journeys 1–5 produces a correct, complete `audit_events` row — this journey is run as a meta-check across the others, not standalone).
7. **Cross-tenant isolation probe** (org A user attempts every operation above against org B's data via direct request manipulation, all denied).
8. **Prompt-injection fixture run** (a malicious CV/JD is processed through the full pipeline; verify score/gate outcomes are unaffected and no injected instruction executes).

## 16.3 Mobile Testing — Build Phase 13

### Stack and conventions

`apps/mobile` tests run under **jest-expo** (a preset that ships RN/Expo's own native-module mocks) + **`@testing-library/react-native`** (`render`/`screen`/`fireEvent`/`waitFor`, the RN equivalent of Testing Library's DOM API), not Vitest — Vitest cannot execute React Native component code (no DOM, native module surface differs entirely), so this is a deliberate second test runner for this one package, not an inconsistency. `apps/mobile/jest.setup.js` mocks `expo-secure-store`, `expo-font`, `react-native-safe-area-context`, and `react-native-reanimated` (the last three via each package's own official jest mock) so every screen renders without a native runtime.

Established mocking conventions (set in Waves 2–5, reused rather than reinvented throughout Wave 6's additions):

- **Fake Supabase client** — `__tests__/test-utils/supabaseMock.ts`'s `createFakeSupabase(routes)` builds a minimal thenable query-builder keyed by table name; a route is either a fixed `{ data, error }` or a function (called fresh per invocation, so a table queried twice with different filters in one screen — or across a refetch — can serve different results). **Critical stability rule, learned the hard way in Wave 6:** the object `getSupabaseClient()` returns must be the SAME reference across renders (a fresh object literal per call breaks `useSupabaseQuery`'s `useEffect` dependency array and causes an infinite render loop that OOMs Jest — confirmed directly, not theoretical). `createFakeSupabase` itself is fine (its caller typically does `mockGetSupabaseClient.mockReturnValue(createFakeSupabase(...))`, which IS stable across the mock's lifetime); a test that instead constructs its own inline fake client for a full-navigator render must build it once, outside the `jest.mock()` factory, exactly like the real module's `cachedClient` singleton.
- **`@/lib/supabase/client`** — `jest.mock`'d to a `mockGetSupabaseClient` jest.fn(), so each test controls exactly what a screen's reads see.
- **`@/lib/auth/AuthProvider`** — `jest.mock`'d to a fixed `useAuth()` return for most screen tests (`FAKE_USER` from the shared mock, `supabaseConfigured: true`); the REAL provider is exercised directly (unmocked) in `__tests__/auth/AuthProvider.test.tsx` and `__tests__/session-expiry/sessionExpiryEndToEnd.test.tsx`, which instead mock `@/lib/env`'s `supabaseConfigured` constant and `@/lib/supabase/client`'s `getSupabaseClient()`.
- **`@/lib/api/client`** — `jest.mock`'d with `jest.requireActual` spread, overriding only the specific mutation wrapper(s) a test needs (`submitGateOverride`, `approveOutreachMessage`, etc.) so the real `ApiResponseError`/`ApiNetworkError` classes and every other export stay real.
- **`@/lib/network/networkStatus`** — `jest.mock`'d with `jest.requireActual` spread, overriding only `useNetworkStatus` to a controllable `{ online: boolean }` for offline-path tests.
- **`require('../test-utils/supabaseMock').FAKE_USER`** inside a `jest.mock()` factory (not a top-level `import` reference) — Jest's mock-factory hoisting forbids referencing an out-of-scope variable unless its name is prefixed `mock`, so every screen test's `AuthProvider` mock reaches for `FAKE_USER` via `require(...)` inside the factory rather than importing it at module scope.

### iOS / Android / small-screen verification — static analysis substitute (honest limitation)

**This build environment has no Xcode, Android SDK, or device/simulator of any kind — confirmed by every prior Build Phase 13 wave and re-confirmed this wave.** No real iOS or Android device/simulator testing has been performed at any point in this phase, and none should be claimed. In its place, Wave 6 ran a static-analysis pass:

- **Platform-specific code:** `grep`'d the whole `apps/mobile` source tree for `Platform.OS`, `'ios'`/`'android'` literals, and any platform-exclusive API usage. Exactly one call site exists: `screens/home/CopilotConversationWorkspaceScreen.tsx`'s `<KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : undefined}>` — a correctly-guarded ternary with an explicit `undefined` (no-op) fallback for Android, not an iOS-only code path that would break on Android. No other platform-conditional code, and no iOS-only or Android-only native library, exists anywhere in the app.
- **Small-screen layout:** every top-level screen except the still-stub `CandidateProfileScreen` (never in this phase's 16-screen scope) renders through `components/ui/ScreenContainer.tsx`, which wraps content in `SafeAreaView` (`react-native-safe-area-context`) and applies the design system's 16px outer margin consistently — confirmed by reading the component and grepping every screen file for `ScreenContainer` usage. No screen uses `Dimensions.get(...)` for absolute sizing (grepped, zero matches) — every layout is flexbox-based, which reflows correctly at any screen width. Two small fixed-`width` style rules exist in the whole app (a 56px label column in `NotificationPreferencesScreen` and an 8px unread-dot in `NotificationsScreen`) — both are small, non-content-bearing UI chrome, not a layout assumption that would break on a small screen.

This is a real, known limitation of the environment, stated plainly rather than glossed over — it substitutes for, and does not claim to replace, real device/simulator QA before any release.
