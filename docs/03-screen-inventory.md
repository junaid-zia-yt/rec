## 3.3 Per-Screen Requirement Template (illustrative — screen 18, the one confirmed screen)

- **Visible data:** candidate name, rank, overall %, gates passed/total, evidence %, per-criterion values with qualifiers, strengths/risks prose.
- **Primary actions:** select/deselect finalist, continue to shortlist.
- **Secondary actions:** open full candidate dossier, request more evidence (per DESIGN.md's "Request Audit Evidence" pattern).
- **Required entities:** `candidate_role_matches`, `mandatory_gate_results`, `requirement_evidence`, `scoring_breakdowns`, `shortlist_candidates`.
- **Required API ops:** `GET /projects/:id/finalists`, `POST /shortlists/:id/candidates`.
- **AI functionality:** match score and evidence percentage are AI-assisted but must be deterministically recomputed/validated per [[08-candidate-scoring]] — the UI must never display an AI number that skipped deterministic gate validation.
- **Validation:** cannot "Continue" with 0 candidates selected; cannot select a candidate with a failed mandatory gate (UI-level enforcement of Core Principle #4/#5).
- **States:** loading (skeleton cards), empty (no finalists yet), error (score computation failed — show stale score with a "recalculating" badge, never a blank), permission-denied (client decision-maker sees a read-only variant with no "Continue" button).
- **Audit:** every selection change and the final "Continue" action is an `audit_events` row with actor, timestamp, before/after state.
- **Desktop vs. mobile:** mobile stacks the three finalists vertically per DESIGN.md Doc B; desktop is expected to use the 35/65 split-pane pattern from Doc A (list left, detail right) — **[GAP]**, no desktop screenshot confirmed.
- **Design-only or coded:** design-only (Stitch export); no usable frontend code exists yet — see [[02-asset-inventory]].

## 3.4 Implementation status notes (appended per build phase)

- **Screen 15 — Quality review / score override.** Implemented Build Phase 8, consolidated onto one screen rather than as a standalone route: `apps/web/components/domain/shortlists/review-queue-panel.tsx`, reached from the "Quality review" tab of `/shortlists` (`apps/web/app/(app)/shortlists/page.tsx`). This is a deliberate scope decision, not a partial build — the brief's queue/decision-dialog/verification-request steps are one panel with an inline reviewer-decision dialog and an inline "request verification" trigger, rather than three separate screens/routes, so a reviewer never leaves the queue to act on a candidate. The underlying gate/score data itself (mandatory gate results, weighted-scoring breakdown, AI vs. deterministic result) remains the candidate detail page's "Evaluation" tab, built Build Phase 7 (`apps/web/components/domain/candidates/candidate-evaluation-panel.tsx`) — screen 15's queue links into that tab rather than duplicating it.
- **Screens 18/19 — Shortlist (Verification Matrix / Finalist Comparison) and Client shortlist approval.** Implemented Build Phase 8: `apps/web/app/(app)/shortlists/[shortlistId]/page.tsx` now renders a live workspace (`shortlist-workspace-panel.tsx`/`shortlist-builder-panel.tsx`) against real Supabase data when configured, and falls back to the original Build Phase 1 demo "Verification Matrix" screen — extracted verbatim, unchanged, into `apps/web/app/(app)/shortlists/[shortlistId]/demo-view.tsx` — when it is not. Client Decision-Maker's read-only approve/discuss/reject view (screen 19) is the same route, gated by the role's narrowed RLS/permission scope (docs/06-roles-permissions.md §6.2.6) rather than a separate URL. Two honest gaps, not hidden: (1) no dedicated mobile-only shortlist/comparison layout was built beyond the existing responsive Tailwind layout — the brief's "mobile stacks the three finalists vertically" is satisfied by responsive flow, not a distinct mobile screen; (2) the live comparison view is simpler than this section's illustrative Build Phase 1 demo template (§3.3) — `DEMO_COMPARISON`'s siteCount/headcount/plVolume/domain/city/distance fields have no backing columns anywhere in the schema (known since Build Phase 7, still unresolved), so the live view shows only what is actually backed: score, gates passed, evidence %, completeness %, and the recruiter's note. No dedicated "decision history" screen exists yet either — history is readable via `shortlist_activity`/`client_decisions` but has no history-specific page — a natural Build Phase 9 candidate.

- **Screens 28/29 — Recruiter AI copilot.** Implemented Build Phase 11: `apps/web/app/(app)/copilot/page.tsx` (conversation list/start form, `copilot-start-form.tsx`) and `apps/web/app/(app)/copilot/[conversationId]/page.tsx` (the chat workspace, `copilot-conversation-workspace.tsx`). The workspace renders each turn's inline tool-call activity (tool name, whether it was denied), citations, and two safety caveats surfaced directly in the assistant's rendered text rather than hidden in metadata: an unsupported-claim strip notice and a missing-citation notice (`detectSafetyCaveats()` — a **text-heuristic** that pattern-matches the guardrail's own caveat phrasing in the persisted message content, not a dedicated structured field on `copilot_messages` for either flag; flagged as a known fragility in docs/build-phase-11-report.md §5, since a future prompt-wording change to either caveat's phrasing would silently break this without a compile-time signal). A confirmation-dialog affordance (`PendingToolConfirmation`) exists in the component for a future mutating tool's `requiresConfirmation: true` flow — it is currently inert scaffolding, since none of the copilot's 13 tools can mutate anything (docs/07-data-model.md §7.12). No cancel-in-flight control exists; a long-running turn is instead bounded by the orchestration layer's own hard 45-second timeout (docs/09-ai-architecture.md §9.9), not a user-triggered cancel — the UI's `cancelled` status branch exists for a future cancel affordance but nothing in this build ever produces that status today.

- **`/integrations` (rewired), `/settings/jobs` (new), `/notifications` (rewired off legacy demo data), `/settings/notifications` (new) — Build Phase 12.** `/integrations`: the per-provider status list (`apps/web/app/(app)/integrations/page.tsx`), now backed by `lib/integrations/load.ts`'s real `loadIntegrationConnections` — renders every provider consistently for every role, but shows real connection detail (mode, status, account owner, last sync) only for `agency_admin`/`platform_admin`; every other role sees an honest "ask an agency admin" affordance rather than a blank or misleadingly-empty list (docs/06-roles-permissions.md §6.2.9). Connect/disconnect/trigger-sync/record-account-owner actions are `agency_admin`-only. `/settings/jobs`: the admin-only "Job status" oversight screen (`app/(app)/settings/jobs/page.tsx`) — status counts, a filterable job list, and a manual-retry action per dead-lettered/failed row; deliberately never renders a job's raw `payload`/`last_error` JSON, only a short structured failure summary (`lib/jobs/load.ts`'s own "never surfaces payload" discipline). `/notifications`: the in-app notification center (`app/(app)/notifications/page.tsx`), replacing Build Phase 1's static demo data with `lib/notifications/load.ts`'s real, own-recipient-only list; every notification's link is resolved via `buildPermissionSafeDeepLink()` fresh at render time (never stored/cached), so a notification whose underlying resource is gone or whose access was since revoked renders as plain, unlinked text rather than a broken or stale link. `/settings/notifications`: per-event-type in-app/email preference toggles (`app/(app)/settings/notifications/page.tsx`), own-user only.

- **Native mobile application (Expo React Native) — Build Phase 13.** All 16 mobile-relevant screens from the inventory above are now implemented as real, tested Expo screens (not stubs): Sign in (#1), Home dashboard (#2), Project list (#3), Project details (a mobile-scoped view of #4), Job scorecard (a read view of #7/#8), Candidate pipeline (#14), Candidate evaluation (mobile's version of #15, including the human-override sheet), Evidence review (#13), Candidate comparison (#20), Outreach approval (mobile's version of #16/#17's approval step), Final shortlist (#18, the Verification Matrix), Client decision (#19), POC comparison (a mobile read view of #21), Notifications (#26), More/Settings including Notification preferences (#27), and the Recruiter AI copilot conversation workspace (#28/#29). Architecture: a React Navigation v6 Auth-stack ⇄ Main-tabs root switch, direct RLS-scoped Supabase reads for everything except a small set of higher-risk mutations (gate override, outreach approval, shortlist internal approval, client decision, notification read/preferences, copilot turn) which route through a new bearer-authenticated `apps/web/app/api/mobile/*` layer — see [[13-api-service-boundaries]] §13.8. One screen in the original navigation graph, `CandidateProfile` (mobile's mirror of screen #11), remains a stub route (typed, wired into navigation, no real content) — it was never in this phase's explicit 16-screen brief list and is flagged here as a natural next-wave candidate, not a silent gap. Full phase detail, wave-by-wave, is in [[build-phase-13-report]].
